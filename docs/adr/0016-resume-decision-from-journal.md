# ADR-0016：用自己的 journal 终态区分「崩溃」与「业务失败」

- 状态：Accepted
- 日期：2026-09-05

## 背景

一个 Agent 任务失败重来时，要判断是哪一种：

- **worker 进程崩了 / 租约超时** → 应当**接着上次跑**，别浪费已经花掉的 token
- **业务上真的失败了** → 应当按 `resumePolicy` 决定是否从头重来

Conductor 侧分不出来：responseTimeout 超时会把任务判 `TIMED_OUT` 并推进 `retryCount`，
业务失败重试同样推进 `retryCount`（v0.3 §2.2 已核实）。这个问题从 v0.3 起悬着，
当时的处理是「默认 `on-lease-loss`，优先保护成本，待真实业务验证」。

## 决策

**不从 Conductor 的 `retryCount` 反推，改看我们自己的 journal 有没有写下终态。**

| 上一次尝试的 journal | 说明 | 处理 |
|---|---|---|
| **无终态条目**（没有 `final`，也没有错误收尾） | worker 半路没了：进程崩溃、被 kill、或租约超时后被判 `TIMED_OUT` | **续跑**，重放已有 journal |
| **有终态条目** | 正常跑完并判定失败，由 Conductor 按 `retryCount` 重试 | 按 `resumePolicy` 决定是否重开 |

`resumePolicy` 保留，但语义收窄为「**业务失败之后**是否从头重来」，不再承担区分职责。

## 理由

1. **判据在自己手里**。worker 有没有跑完，是我们自己写下的事实，不需要向编排引擎打听。
2. **不受 Conductor 语义变化影响**。`retryCount` 的推进规则是服务端实现细节，
   跨版本可能变；journal 是我们自己的数据结构。
3. **顺带解决了一类静默错误**：原来若判错方向，要么重复付费（该续跑却重开），
   要么在脏状态上继续（该重开却续跑）。现在这两种情况都由一个确定性判据裁决。

## 前提

写终态条目必须是**回写 Conductor 之前**的最后一步，且带 fence 校验（§5.3）。
否则会出现「journal 写了终态但 Conductor 没收到结果」的窗口 —— 此时任务重投会被误判为业务失败。
该窗口无法完全消除（两次写入不在一个事务里），但把顺序定成
「先写 journal 终态 → 再回写 Conductor」可以保证误判方向是**安全的那一侧**：
最坏情况是把一次租约丢失当成业务失败重跑，浪费成本但不会在脏状态上继续。

## 代价

- 增加一次 journal 写（终态条目）。相对被保护的 LLM 成本可忽略。
- `resumePolicy: 'never'`（不落 journal）下本判据不可用，此时退回原有行为并在启动时告警。
